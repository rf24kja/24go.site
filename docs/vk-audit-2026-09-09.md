# VK Integration Audit — 2026-09-09

## Critical Issues (will break in production)

### 1. `wall.post` missing `random_id` — duplicates on retry
**File:** `vk_poster.py:113`
```python
vk.wall.post(owner_id=owner_id, message=text, from_group=1)
```
**VK API requires** `random_id` (unique int per request). Without it:
- Retries create duplicate posts
- VK may reject the call entirely
**Fix:** Add `random_id=random.randint(0, 2**31)` or use UUID-based int.

### 2. `VK_GROUP_TOKEN` from env — breaks multi-tenant
**Files:** `vk_poster.py:98`, `vk_comment_scraper.py:62`, `vk_group_scanner.py:61`
```python
group_token = os.getenv("VK_GROUP_TOKEN", "")
```
Every VK task reads a **single global token** from env. This means:
- All tenants share one token
- Rate limits hit faster
- One ban kills all VK operations
**Fix:** Fetch token from `account_sessions` table per `account_id`.

### 3. Group scanner uses `messages.getLongPollServer` instead of `groups.getLongPollServer`
**Files:** `vk_listener.py:64`, `vk_group_scanner.py:90`
```python
server_info = vk.messages.getLongPollServer(group_id=group_id)
```
**VK docs:** For group events (wall posts, comments, member joins), use `groups.getLongPollServer`. The `messages` LongPoll only delivers **private messages** to the community.
**Result:** Wall posts and comments are never detected in real-time.

### 4. `connect-vk` doesn't validate the token
**File:** `accounts.py:1032-1061`
Stores the token without verifying it works. Should call `groups.getById` or `groups.getTokenPermissions` first.
**Also:** `group_id` is accepted as a parameter but **never stored** in the database.

## High Priority Issues (data loss / incorrect behavior)

### 5. Comment scraper — no pagination
**File:** `vk_comment_scraper.py:80-87`
```python
vk.wall.getComments(owner_id=owner_id, post_id=post_id, count=max_comments, ...)
```
`max_comments` defaults to **10**. Posts with 50+ comments lose data. VK supports `count=100` with `offset` pagination.
**Fix:** Loop with `offset` until all comments fetched or limit reached.

### 6. `wall.getComments` returns nested threads poorly handled
**File:** `vk_comment_scraper.py:89-135`
The scraper treats all comments flat, but VK returns threaded comments (replies to comments). Thread replies (in `thread.items`) are ignored entirely.

### 7. `RateLimiter.is_allowed` — race condition
**File:** `anti_ban.py:35-53`
```python
pipe.incr(hourly_key)  # increments first
...
if hourly_count > max_per_hour:
    pipe2.decr(hourly_key)  # reverts after
```
Multiple concurrent workers can all pass the check before any revert. Use `INCR` + check + `DECR` atomically, or use Lua scripts.

### 8. `RateLimiter.wait_if_needed` — shared wait key across action types
**File:** `anti_ban.py:61`
```python
wait_key = f"rate:{account_id}:wait_until"  # no action_type!
```
A wall_post action sets wait, blocking message actions too.

### 9. `_scraped_cache` / `_seen_vk` — in-memory, lost on restart
**Files:** `vk_comment_scraper.py:22`, `vk_group_scanner.py:23`
Per-worker in-memory dicts. If worker restarts, all dedup state is lost → duplicate leads.
When cache fills (10K), `clear()` wipes everything.

### 10. Long Poll event parsing uses positional array indexing
**Files:** `vk_listener.py:112-115`, `vk_group_scanner.py:128-131`
```python
if event[0] == 4:
    flags = event[1]
    peer_id = event[3]
    text = event[5]
```
VK LP v2 format differs. The `text` field position varies. Should use the documented LP event structure or `messages.getLongPollHistory` for reliable parsing.

## Medium Priority Issues (missing features)

### 11. No flood wait handling (error 921)
VK returns error 921 with a `wait` field. Current code doesn't catch this and sleep.

### 12. No proxy support
`vk_api.VkApi(token=...)` never receives a `proxy` parameter. VK recommends different IPs per account.

### 13. `_set_vk_status` creates new Redis connection every call
**File:** `vk_listener.py:191`
```python
r = redis.Redis.from_url(os.getenv("REDIS_URL", ...))
```
Called every 30 seconds via heartbeat. Should use a cached connection.

### 14. `users.get` called per-comment without batching
**File:** `vk_comment_scraper.py:110-118`
VK supports `users.get(user_ids="1,2,3")` up to 1000 IDs. Current code makes 1 API call per comment.

### 15. No warmup integration in actual task flow
`WarmupManager` exists but is never called from `vk_poster`, `vk_listener`, or `vk_comment_scraper`.

### 16. No error code handling
None of the VK tasks handle specific VK errors:
- `900` — can't send messages (privacy)
- `901` — can't send to communities
- `921` — flood control
- `300` — wall disabled
- `15` — access denied

### 17. VK group discovery doesn't filter by members count
**File:** `groups.py:717-727`
Returns all results without filtering by `members_count`. Small groups (10 members) pollute results.

---

## Low Priority Issues (code quality)

### 18. Session cache `_vk_sessions` is a plain dict
No TTL, no size limit, no eviction. Long-running workers leak memory.

### 19. `asyncio.new_event_loop()` pattern repeated in every task
Every Celery task creates and destroys an event loop. Could use a shared loop or `asgiref.sync_to_async`.

### 20. No VK token refresh mechanism
If a token is revoked/deleted, the session is cached and will keep failing until worker restart.

### 21. `wall.post` called without `close_comments` option
For lead gen, you want comments enabled (to scrape them), but there's no option to control this.

### 22. No `attachments` support in posting
`wall.post` only sends `message` text. No photo/video/doc upload support.
